# Go 后端的工程骨架：先分清责任，再复用模板

## 一句话模型

规范项目不是目录越多越好，而是输入、业务、持久化、生命周期和验证各有明确边界，别人能安全修改并验证它。这里是结合本项目的实践建议，不是“Go社区唯一架构标准”。

## 必须掌握

适合当前规模的骨架：

```text
cmd/apiserver        配置、依赖装配、启动/停止
internal/catalog    模型、业务规则、消费方需要的接口
  transport/http    请求解析、错误与响应映射
  postgres          SQL调用、事务、SQLSTATE与模型转换
    sqlcgen         只生成，不手改，不暴露给业务/HTTP
internal/platform   已有共享用途的配置、数据库连接、探针和日志
db                  schema / migrations / queries 各有真源
scripts             小而明确的工程操作入口
docs                决策、操作、证据、学习分开
```

它不是要求所有项目都分三层。简单服务可更小；接口应在需要替换或测试的边界出现，不为每个struct机械创建同名接口。不预建无真实用途的pkg、util、通用CRUD或依赖注入框架。[Go官方布局建议](https://go.dev/doc/modules/layout)按模块用途给出不同组织方式，不能把某个模板仓库当成官方规范。

标准而高效的写法优先降低理解与变更成本：

- gofmt交给机器；命名表达业务，不编码框架细节；构造时显式传依赖，避免隐藏全局状态。
- ctx沿请求向下传，明确超时预算、取消和资源所有权；创建goroutine必须能回答谁停止、谁等待、错误如何返回。
- 早返回压平分支；错误用 `%w` 保留链，边界用 errors.Is/As分类；避免每层重复记录同一个错误。
- 参数化SQL，数据库约束保证最终一致性；不要用“先查再插”代替唯一约束。
- 事务中的所有SQL使用同一tx；提交失败也是失败；不要在事务内进行不必要的慢网络调用。
- 性能优化先量化工作量，再改实现；不以减少几行代码、盲加并发或抽象数量衡量效率。

## 容易混淆或踩坑

“社区惯例”“团队约定”“项目取舍”不是一回事。gofmt、标准错误/context语义适合广泛遵循；固定三层、某个框架、目录名或某个ORM不是普遍强制标准。Effective Go对语言习惯仍有价值，但官方明确说明它不涵盖许多后来的语言与生态变化，不能当成现代工程的完整规范。

模板应保存稳定的不变量、检查入口和替换点，不复制某项目的凭据、端口、业务状态或未证明的生产参数。常见选择用短说明；涉及持久化/安全/成本或难撤销的决定才写ADR，避免文档本身变成负担。

## 在本项目中的落点

沿 `cmd/apiserver/main.go → catalog HTTP → service → postgres repository → sqlcgen` 追踪一次Service创建。明确事务归属、SQLSTATE如何变成领域错误，再变成HTTP状态；不是把所有层“写齐”就算掌握。代码真源和依赖边界见[架构](../../architecture/overview.md)。

## 最小验证实验

选一个真实变更，写清正常、非法、冲突和依赖失败四类结果；先静态审阅，再运行最小相关测试和完整门禁。用一次错误定位证明自己能沿边界找到原因，而非只确认200。已有实例见[查询计划报告](../../benchmarks/m1-service-list-query-plan.md)。

## 面试表达

“我选择模块化单体，接口隔离业务与存储，显式控制事务和错误映射；通过真实数据库与生成一致性测试验证边界，不提前造通用框架。优化基于执行计划而不是猜测。”
