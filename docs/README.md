# 项目文档说明书

本目录是项目的“施工手册、学习笔记和证据库”。它和源码一起提交到 Git；聊天记录不是项目真源。

所有正式文档使用 UTF-8、LF 换行的 Markdown。Windows 记事本可以直接打开、编辑并保存 `.md` 文件；Markdown 只是带少量标记的普通文本。

## 新对话或新会话的最小阅读集

任何新会话都先阅读下面五项，才能继续实现而不丢失上下文：

1. `project-context.md`：项目为何存在、当前边界和长期原则。
2. `standards/README.md`，以及相关的命名、Go、API 规范。
3. `progress/current.md`：上一次停在哪里、什么已验证、下一步是什么。
4. `stages/README.md`，再进入当前阶段的 `plan.md`、`contracts.md`、`checklist.md`。
5. 与当前任务直接相关的 `architecture/`、`knowledge/` 或最近的会话记录。

读取顺序很重要：先读稳定规则，再读当前状态，最后读具体任务。这样阶段计划不会覆盖全局规范，旧会话也不会被误当成当前事实。

## 原始方案材料

仓库外层的 `reference/` 保存原始方案书、目标岗位材料和历史调查材料。它们是路线的原始依据，不是日常施工入口。

只有以下情况才回读完整原始材料：路线发生实质调整、当前阶段边界存在争议、需要核对方案书的具体承诺、或新会话发现本目录的上下文不足。日常施工只读“最小阅读集”和当前任务相关知识笔记。

## 目录总览

```text
docs/
├── README.md                 本说明书：目录、阅读路径和真源规则
├── project-context.md        项目的长期目标、边界、术语和工程原则
├── standards/                持续生效的命名、Go、HTTP、文档规范
├── architecture/             当前已实现架构、技术提案和 ADR 决策记录
├── stages/                   M0–M8 的阶段施工包
├── progress/                 当前交接页和每次工作会话记录
├── knowledge/                精要系统的知识笔记与术语表
├── runbooks/                 可复制执行的运行、迁移、排障步骤
├── benchmarks/               性能、资源与容量实验的证据
├── postmortems/              故障实验、事件和改进复盘
└── templates/                新阶段、会话、知识笔记的统一模板
```

## 每一类文档放什么

| 位置 | 应放内容 | 不应放内容 |
| --- | --- | --- |
| `project-context.md` | 稳定目标、范围、核心术语 | 每日进度、具体实现细节 |
| `standards/` | 跨阶段持续有效的规则 | 单一功能的临时实现方案 |
| `stages/m?-*/` | 本阶段施工步骤、精确契约、验收、结果 | 其他阶段的完整设计 |
| `progress/current.md` | 当前唯一事实、下一步、阻塞项 | 已过期的详细历史 |
| `progress/sessions/` | 每次结束时的可恢复交接记录 | 密钥、私有运维信息 |
| `knowledge/` | 经提炼的原理、项目落点、最小实验 | 未筛选的网页复制内容 |
| `architecture/overview.md` | 已实现组件和实际数据流 | 尚未做的远期架构图 |
| `architecture/proposals/` | 尚未决定的重要选型、想法、备选项和待验证假设 | 已定案的最终规范 |
| `architecture/decisions/` | 有理由、有后果的技术决策（ADR） | 纯任务清单 |
| `runbooks/` | 可执行且经过验证的操作步骤 | 未测试的猜测性命令 |
| `benchmarks/` | 环境、参数、结果、限制 | 脱离拓扑的性能结论 |
| `postmortems/` | 事件时间线、证据、改进验证 | 归责性描述 |

## 真源与防漂移规则

- **完整可运行代码**：只以源码目录和 Git commit 为准，文档不复制整份实现。
- **接口与命名**：以当前阶段的 `contracts.md` 和 `standards/` 为准；代码完成后必须与其一致。
- **当前进度**：只以 `progress/current.md` 为准；旧会话只作历史证据。
- **已实现架构**：只以 `architecture/overview.md` 和实际代码为准。
- **技术取舍**：以 ADR 为准；新决策不回写篡改已接受的旧 ADR。
- **实验结论**：以对应 benchmark、postmortem 和可重放命令为准。

## 工作节奏

开始工作：更新任务理解后，先读“最小阅读集”，再按当前阶段 `checklist.md` 施工。

结束工作：更新 `progress/current.md`，从 `templates/session.md` 建立会话记录，填写验证结果和下一次的具体入口；有代码变更时将文档与代码一起提交。

阶段结束：填写 `outcome.md`，更新当前架构与 ADR，冻结证据；再进入下一阶段。

## 阅读提醒规则

默认由协作助手根据事件提醒并引用具体文件；你不需要主动遍历全部目录。

| 触发事件 | 应阅读的位置 | 目的 |
| --- | --- | --- |
| 每次开始或恢复施工 | `progress/current.md` 与当前阶段施工包 | 恢复准确上下文和下一步。 |
| 将要手写一个新模块、类型或 API | 当前阶段 `contracts.md` 与相关 `standards/` | 保持目录、包、接口和错误语义一致。 |
| 学习或实现陌生技术 | 对应 `knowledge/` 笔记 | 先建立完成当前实验所需的最小模型，实践后再补充和提炼笔记。 |
| 出现尚不能可靠收敛的重要技术选择 | `architecture/proposals/`；决定后看/写 ADR | 留下取舍理由，避免以后只记得结论。 |
| 运行容器、迁移数据或排障 | 对应 `runbooks/` | 只执行已经验证的操作步骤。 |
| 准备提交、推送或合并 GitHub 变更 | `runbooks/github-ssh.md` | 恢复 SSH agent，并按“分支 → PR → required checks → 合并 → 同步 main”完成受保护分支流程。 |
| 做压测、故障实验或阶段收尾 | `benchmarks/`、`postmortems/`、`outcome.md` | 保存可解释的证据和实际结果。 |

## 方案解释规则

当协作助手新增或建议重要接口、目录、依赖、存储、部署方式或架构边界时，必须同时说明：要解决的问题、选择该方案的原因、至少一个替代方案及不选它的原因、适用边界和下一步验证方式。简单的机械性改动不需要重复展开。

## 决策协作规则

- 项目采用“边做边学、先实践后总结”的节奏。常见、典型、有学习价值且可从现有约束可靠判断的工程选择，由协作助手直接收敛并推进；项目所有者通过亲自手敲、运行和复盘形成理解。
- 协作助手作出重要选择时，用简短说明交代要解决的问题、推荐理由、主要替代方案、不选原因、适用边界和验证方式；不要求项目所有者在每个常规选择前逐项批准。
- 只有选择高度依赖个人偏好或未提供的现实条件、多个方案在当前证据下无法可靠区分，或涉及新成本/外部授权、安全边界、不可逆数据操作和显著路线变更时，才暂停施工并请求项目所有者确认。
- 请求确认时简要介绍可行选项、主要利弊、推荐项和暂不决定的后果；项目所有者保留质疑、修改和最终决定权。
- 已收敛且长期生效的关键决定记录为 ADR；真正尚在比较的选择记录为提案；阶段结束时将实际结果和偏差写入 `outcome.md`。

## 信息安全

任何文档都不得提交密码、token、SSH 私钥、真实 IP、账单、私有备份位置、真实代理端口或未脱敏生产数据。需要表达时使用占位符，例如 `<server-host>`、`<api-token>`。
