# 游标分页：使用索引不等于有效定位游标

本项目的[实验报告](../../benchmarks/m1-service-list-query-plan.md)提供数据、SQL、原始计划和限制；这里记录可迁移的阅读方法。

- 先确认正确性：排序字段、方向、非空约束、游标是否排除自身、同时间戳是否按 ID 继续。数量相同不能证明无漏项，比较有序 ID；空结果的聚合可能为 NULL。
- 再看访问路径：`Index Scan` 只说明用了索引。若 `Index Cond` 只有 team_id，而游标在 `Filter`，仍可能从团队起点扫描再丢弃大量行。
- 本例索引 `(team_id, created_at DESC, id DESC)` 同时服务等值过滤与有序读取；非空 `(created_at, id) < (时间, ID)` 表达字典序边界。混合排序方向或可空字段不能照抄该改写。
- `Limit` 可以提前停止下游扫描；top-N Sort 只限制排序保留规模，不免除读取其全部输入。本例旧索引首页仍读取该 Team 的1000行。
- Buffers 是块访问次数，不是不同块数量；父子节点数字有包含关系，不能相加。Planning 与 Execution 区分，cost 不是毫秒。
- 先看计划结构和工作量，再看时间。正反顺序都测量、预热与正式轮次分开；保留不利结果，不拿单次最快值当稳定收益。
- SQL 字面量实验、真实驱动功能测试、HTTP 性能测试回答不同问题。SQL 更快不等于端到端固定倍数提速。

本轮没有增加索引，而是让已有索引更有效地服务深页条件。SQL、sqlc 和 adapter 的参数契约仍须逐层核对，不能以生成成功替代真实数据库测试。
