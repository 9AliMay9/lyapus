# ADR-0001：从模块化单体开始

- 状态：accepted
- 日期：2026-07-20

## 背景

项目仍处于 M0，需要先证明 Go 工程质量、HTTP 边界、测试与可复现性。过早拆分服务会增加部署、调试和失败语义的复杂度，却没有真实独立生命周期或扩缩容需求支持。

## 决策

以单一 Go module 和单一 `apiserver` 进程开始。业务能力以 `internal/` 下边界明确的包组织；只有出现真实的独立部署、故障隔离或生命周期需求时才拆分。

## 后果

- 近期开发与调试更简单，M1 可以专注于 API、SQL、事务和测试。
- 模块边界必须保持清晰，避免单体演化为无结构的共享代码堆。
- M2 可增加受控故障工作负载，但不要求立刻将控制面拆成多个服务。

## 备选方案

- 从第一天拆为多个微服务：拒绝，当前没有足够业务边界和运行收益。
