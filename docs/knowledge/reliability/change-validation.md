# 升级与验收：减少重复，不减少保障

## 一句话模型

每个检查回答一个明确风险；证据绑定版本、配置和环境。复用的是仍然有效的证据，不是过去出现过的PASS。

## 必须掌握

一个可复用的变更记录只需覆盖：

1. 动机：已遇到的问题或收益，为什么现在做、不做会怎样。
2. 差异：锁定旧/新版本、源码commit、依赖与授权变化，区分发行版和源码版。
3. 影响：改变了哪些运行路径，哪类数据或客户端可能受影响。
4. 验证：正常、错误、兼容接续、完整性与清理的预期结果。
5. 回退：撤销代码/二进制能否恢复，数据库状态是否已经不可逆改变。
6. 证据：命令、退出码、结果、目标与提交，不提交秘密。
7. 门禁与责任：谁执行、失败时停止在哪里、何时才能发布。

把计划写成“小矩阵”：风险 → 唯一主测试 → 成功/失败条件 → 证据位置。无需为同一SQL改变先跑十轮手工全流程；先局部验证，失败再定位，通过再一次完整回归。已有正确性测试、性能实验、交付检查各自证明不同事，不能简单合并为“都测试过”。

## 容易混淆或踩坑

- 本地重复和CI重跑不同：纯文档补交可复用本地运行证据，但最新提交的required CI不能引用旧结果绕过。
- API验收库与清表测试库应隔离，即使多建一个库有成本，也不是无意义重复。
- 旧版建库→新版接续与新版空库全部apply不同；工具升级要覆盖前者，不能只做后者。
- 应用漏洞扫描不自动覆盖构建工具、镜像OS包或下载的二进制。分别识别扫描对象和能力限制，零发现不是完整安全证明。
- 升级并非总要独立PR：小且相关的工具变更可作为同一交付目标的独立commit；跨功能、跨授权、大规模适配应拆开。既不要机械拆分，也不要为了少跑CI混入无关变更。
- 不把“全量回归通过”当成“数据可恢复”；备份存在与恢复演练成功也不同。

## 在本项目中的落点

[Atlas与最终验收计划](../../stages/m1-go-backend/atlas-upgrade-acceptance-plan.md)把安全依赖更新、迁移兼容性、应用回归和空环境演示分开；同一PR两轮CI用于候选与最终文档提交，不递归增加“记录最终成功”的提交。

## 最小验证实验

### 本轮形成的操作习惯

- 复制的是命令正文，不是shell的 `$` / `>` 提示符；正文里的 `>` 是重定向，可能在程序启动前就截断文件。长命令可以分行，但反斜杠后不能残留字符；重定向符与目标路径放在同一行。
- `"$variable"` 展开为一个参数，`'$variable'` 保留字面量；先核对目标，再执行可能改变数据的命令。
- `$?` 是上一条命令的退出码，立即读取或保存，不能先执行另一条命令再取。退出0只是必要条件，还要核对版本、预期输出与实际状态：本次零字节旧工具文件在Bash下无输出且退出0就是反例。
- 保存候选与旧产物身份、校验补丁，再构建到临时路径，成功后替换默认入口。SHA-256证明内容一致，不证明来源可信；基础commit与补丁审阅仍不可省。
- 第三方工具的依赖补丁不应混进应用go.mod；“工具扫描通过”“应用扫描通过”“迁移兼容通过”分别记录。维护本地补丁需明确撤销条件，不长期无主地背负fork。

这些是失败成本高、可迁移的能力；库方法可以查阅，机械脚本可以辅助生成，但目标、退出条件、数据影响与失败定位需要亲自理解。本轮实例见 [正式复盘](../../progress/sessions/2026-10-01-m1-final-acceptance.md)。

对迁移目录临时副本修改内容，预期checksum拒绝；保留真源不变。对同一测试库重复apply，预期无待执行文件。执行须在专用资源与明确授权下；本文是学习模型，不是已执行证明。

## 面试表达

“我按变更影响设计覆盖，不靠重复次数制造信心；使用候选身份、兼容接续、负例和最新门禁保证升级，只有输入条件未改变时才复用证据。”
