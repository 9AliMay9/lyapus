# 协作式手敲代码规范

## 目的

项目所有者在本地手敲实现，以获得对代码的直接理解；协作助手负责收敛常见工程决策，并给出正确、可验证且可恢复的施工指引。主要学习方式是“边做边学、先实践后总结”，聊天记录不是项目真源。

## 学习与决策节奏

- 实现前只讲清当前代码块必须知道的问题、选择理由、主要替代方案和验证方式，避免在没有具体对象时一次灌入全部理论。
- 项目所有者亲自手敲核心源码；协作助手先静态复查，修正并复查通过后，项目所有者再运行验证并观察结果；协作助手检查运行证据，再结合刚完成的实现解释原理、风险、演进路径和面试表达。
- 常见、典型且能根据项目约束可靠判断的选择，包括有学习价值的依赖、内部接口和实现模式，由协作助手直接决定并简要说明，不逐项等待批准。
- 未确认技术栈按“项目主方向 → 原始方案与已有 ADR/阶段契约 → 目标岗位的泛用能力 → 上游事实与本地实验”顺序收敛；主方向是 Go 可观测性、可靠性、平台工程和基础架构后端。协作助手负责主动检索相关文档与外层 `reference/`，不把逐份翻阅材料转嫁给项目所有者。
- 高度个性化、缺少必要现实条件、难以从证据区分，或涉及新成本/授权、安全、不可逆数据操作和显著路线变化的选择，才与项目所有者协商确认。
- 项目所有者可随时质疑或要求重审选择；协作助手应以代码、上游文档和可重复实验说明依据，而不是以工具热度或“大厂都在用”代替证据。

## 代码交付方式

- 协作助手在对话中一次交付一个目标文件或一个边界明确的代码块，必须标明目标路径，并提供完整可粘贴/手敲的内容和必要的简短说明。
- 新增或替换代码时，协作助手必须给出可稳定定位的插入锚点（例如“紧接某个类型/函数之后”或“某个测试函数内的指定断言之后”）并简述该位置的组织理由；不依赖易漂移的绝对行号。对于多段、较长或测试密集的文件，必须同时说明代码属于哪个逻辑分组、与相邻代码的先后关系，避免项目所有者在手敲时猜测插入位置。
- 对既有大文件中重复或高度相似文本的局部修正，协作助手必须同时给出检查时的“文件路径 + 行号 + 原文 → 目标文本”；行号用于快速定位，稳定锚点仍是最终判断依据。
- 项目所有者将内容手敲到自己的工程目录；协作助手不默认替其写入源码。只有项目所有者明确要求直接生成或修改某个文件时，协作助手才可写入该目标。
- 文档、README、忽略规则和示例配置等低风险工程文件默认可由协作助手直接维护，再由项目所有者阅读和审阅；核心源码仍遵循亲自手敲规则。
- 每个代码块统一遵循“手敲完成 → 静态复查 → 必要修正与再次复查 → 运行验证 → 下一段”的顺序，适用于所有代码，不以是否涉及数据库或其他外部状态为条件。
- 项目所有者报告手敲完成后，协作助手直接读取目标文件，核对其与交付代码的一致性，并检查参数顺序、SQL、断言、依赖和现有契约。交付代码本身也必须接受审查；发现原方案有瑕疵时说明原因并修正，不能以逐字一致代替正确性判断。
- 复查发现错误时，协作助手先报告问题、影响和精确位置，等待项目所有者修正并再次复查；静态复查通过后，在同一回复给出当前代码块的运行验证命令与预期结果。首次交付代码时可以说明验证目标，但不要求项目所有者在静态复查前直接运行测试。
- 静态复查通过不等于编译、测试或真实运行通过；只有当前代码块的约定运行验证通过并核对证据后，才交付下一段边界明确的源码。格式化可以在复查前完成，但不替代静态复查。

## 本地只读检查与证据传递

- 项目所有者授权协作助手在共享 workspace 中使用只读命令检查源码、生成代码、Git diff、测试配置和文档；不需要项目所有者为长文件内容反复执行 `sed`、复制输出或逐行中转。
- 项目所有者仍亲自执行会改变项目、外部服务或私有环境状态的关键操作，包括手敲核心源码、格式化/生成、测试数据库与容器生命周期、依赖下载、Git commit/push/merge 和 GitHub CLI 操作；协作助手给出命令、预期结果和失败诊断。
- 协作助手若要检查项目所有者刚完成的文件，应直接读取目标路径并报告结论；只有本地无法获得的证据（例如私有终端交互、真实网络错误、Docker 运行输出或 GitHub 页面状态）才请求项目所有者粘贴最小必要输出。
- `sed -n`、`nl`、`git diff` 等只是终端检查手段，不是项目所有者必须执行的固定仪式；项目所有者可用 nvim 或 IDE 阅读源码，协作助手根据检查目的自行选择只读方式。

## 临时接力稿

- 若某个正在手敲的代码块需要防范断联，在 `docs/progress/handoffs/` 创建一份短小完整的接力稿。
- 接力稿必须标明目标源码路径、用途、创建时间、删除条件和验证命令；其内容必须与对话中给出的代码一致，并注明验证命令在静态复查通过后执行。
- 项目所有者报告“已完成”后，协作助手检查目标源码和验证结果。确认无误后立即删除接力稿；若只在本地 Windows 副本完成且尚未同步，则由项目所有者提供文件内容、diff 或验证输出作为确认依据。
- 接力稿是短期恢复材料，不是长期代码副本、发布物或 Git 真源。

## 高能力收口审阅门禁

- 功能性 PR、独立施工包或 M0–M8 阶段准备收口时，默认进行一次高能力一致性审阅。纯文档修正、机械格式化、生成物同步，以及专门承载本次审阅结论的后续文档提交，不递归触发新的同级审阅。
- 触发点是主要实现和验证证据已经具备、但最终文档收口或 PR 合并尚未完成时。协作助手必须先暂停收口工作，明确提醒项目所有者切换到当时可用的高能力模型和合适的推理强度；不能假定或声称已自行识别界面中的实际模型配置。
- 项目所有者明确回复模型或参数已经调整完毕后，协作助手才正式开始审阅。若本次收口开始时项目所有者已经作出该确认，则无需重复切换。
- 审阅至少核对：当前 Git 与可执行实现事实；目录结构、依赖方向和类型边界；当前施工包的 `plan.md`、`contracts.md`、`checklist.md`、`outcome.md`；外层 `reference/` 原始方案的范围与顺序；测试、真实运行和 clean-runner 证据；文档与实现、文档内部以及当前进度入口的一致性。
- 审阅结论必须区分“已实现且有证据”“计划内尚未实现”“有意调整顺序或边界”“意外偏差或缺陷”。可安全收敛的文档同步和小修复直接完成；会改变公共契约、数据模型、安全边界、成本或阶段范围的差异，先向项目所有者说明选项和推荐。
- 完成审阅后再更新当前进度、会话记录、阶段结果和必要的架构/ADR 文档，并运行与变更范围相称的检查。功能性 PR 只有在最新提交的 required checks 通过、收口审阅完成且文档准确记录已有验证和未验证边界后才合并；不得为了消除“待合并”字样而提前声明合并成功。

## 同一 PR 内完成 CI 证据与文档收口

- 2026-09-11 起，默认把实现、测试、CI 证据和相关文档作为同一个施工包，在同一分支、同一 PR 内收口：本地验证后首次提交并创建 PR；第一轮 required CI 通过后补充运行链接、范围、结果及限制，完成收口审阅与文档同步；再次 commit/push 更新原 PR，等待最新提交的 required checks 通过后统一合并、删除分支。
- 第二次 push 是更新原 PR，不另建第二个 PR；若文档与证据已经齐备，不为凑足两次提交制造空改动。CI 失败则修复同一分支并重新验证。
- 一次成功记录只证明对应提交在该次环境运行成功，不保证长期稳定性，也不能代替最新提交的合并门禁。最终 CI 通过后直接合并，不为记录“最终 CI 也成功”再次提交，避免递归。
- CI 与合并实时状态以 PR/Checks 页面为准；文档集中保存代表性 run 链接及结果。实际 squash SHA 或合并后实验可在后续阶段总结中按需补记，不在多个入口反复维护“待 CI／已通过／已合并”。
- 合并后才发现的文档缺陷或新增部署、审计证据可以独立 PR 修正。PR #25 已先合并，因此现有 `docs/post-pr25-sync` 作为一次过渡收尾；它合并后不再为确认该文档 PR 合并而新增文档分支。
- 临时数据库和容器在本轮本地验证结束、不再需要使用时由项目所有者确认目标后清理，并记录实际结果；缺少清理输出时不推断资源已经删除。

## 会话收尾

- 有效会话结束时，更新 `docs/progress/current.md`，并按模板新增会话记录。
- 当一个最小、可验证节点完成时，创建意图清晰的 Git commit；不要用未提交的文档副本代替版本历史。
