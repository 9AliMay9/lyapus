# 可投递 Go 项目与可上生产服务，差在哪

## 一句话模型

生产准入是“在明确业务、数据风险、负载和运维责任下，失败可发现、影响可控、数据可恢复、变更可追溯”，不是装齐某套框架。以下为工程评估清单，不是认证，也不将Google规模要求照搬到个人项目。

## 必须掌握

| 维度 | 上线前至少回答什么 | 当前M1边界 |
| --- | --- | --- |
| 功能与数据正确性 | 契约、边界、并发、事务、重复请求是否符合业务语义 | CRUD/约束/事务/并发及选定分页证据已有；不是穷尽验证 |
| 访问与秘密 | 谁能访问/修改哪些数据；TLS在哪终止；凭据如何最小授权和轮换 | 无应用鉴权/RBAC；Compose本地占位密码，不能原样用于生产 |
| 资源与失败控制 | 请求/SQL/外部调用预算、连接总量、过载保护、退出清理 | 启动/readiness/shutdown有超时；HTTP只有ReadHeaderTimeout，非完整请求预算 |
| 数据恢复 | 数据价值、RPO/RTO、备份隔离、恢复演练与兼容迁移 | 仅可丢弃库重建，没有生产备份恢复证据 |
| 可诊断与响应 | 错误、延迟、流量/饱和度如何发现；谁接告警、如何止损 | 结构化日志/request ID/探针已有；生产告警、值守与恢复目标未建立 |
| 可交付与供应链 | 固定构建输入、候选身份、漏洞维护、审批、回滚/前滚 | 版本锁定与CI已有；完整制品证明、部署回退等未全量演练 |
| 容量与边界 | 预期负载、瓶颈、资源上限、降级、是否必须HA | 只有选定SQL实验，未证明QPS/HA/并发容量 |

“至少”不表示每项必须自己写一套系统：TLS/认证可由合适的平台承担，但责任与验证不能消失。内部低风险工具与公开多租户写接口的准入强度不同；不需要Kafka、Kubernetes或微服务才能上生产，也不能仅凭CI全绿对外承诺生产可用。

## 容易混淆或踩坑

M1原始方案是可运行、可测试、可解释的后端作品，RBAC、压测、遥测等按阶段演进。不能因为尚未生产准入就否定M1可投递价值；也不能把“按工程规范写”偷换成“已生产验证”。本清单用于认识缺口，不自动把所有缺口提升为M1 release阻塞项。

上线真实环境时需要针对威胁模型选择安全要求；OWASP ASVS是可参考的安全验证框架，而不是本项目已通过的认证。生产准入也应针对服务本身，而非用固定目录模板统一判定。

## 在本项目中的落点

截至基线fdf8f25：`NewServer`只配置ReadHeaderTimeout；pool通过New/Ping建立，但没有项目级容量预算实证。Compose端口只绑定回环且使用开发凭据，删除卷流程只针对可丢弃环境。上述边界见源码、[M1契约](../../stages/m1-go-backend/contracts.md)和[交付手册](../../runbooks/compose-delivery.md)，不是本轮要直接扩建的任务。

## 最小验证实验

现有探针中断恢复只能证明该路径恢复，不证明备份、HA或SLO。未来接近真实部署时，先确定RPO/RTO、暴露面和负载，再做对应恢复/权限/过载实验，并记录责任人和失败处理；不要无目标地堆组件。

## 面试表达

“我的M1完成了后端工程基线，能展示正确性、交付和可解释优化；它还不是生产就绪声明。我能指出认证、超时预算、恢复与运维责任缺口，并按实际部署风险设计验收。”

## 延伸阅读

- [Google SRE：生产准入审阅](https://sre.google/sre-book/evolving-sre-engagement-model/)：关注服务特定风险、运行责任与改进，不照搬组织规模。
- [OWASP ASVS](https://owasp.org/projects/asvs)：按应用风险选择安全验证项。
- [Go安全实践](https://go.dev/doc/security/best-practices)：工具链维护、测试与漏洞检查。
