# ADR-0002：跨阶段执行护栏

- 状态：accepted
- 日期：2026-07-27

## 背景

项目在单台个人云主机上同时承担开发、集成、故障实验和演示。若不提前限制压测口径、公开信息、可靠性声明和部署模式，后续很容易把环境偶然结果解释成生产能力，或让 Compose 与 k3s 同时控制同一状态。

## 决策

采用以下四条跨阶段护栏：

1. **双压测拓扑**：远程体验测试与服务端性能测试分开记录。公网结果不等于服务容量；同机发压必须记录资源竞争，必要时使用同地域独立客户端。
2. **公开/私有文档边界**：公开仓库只保存复现实验所需的通用资源、版本、参数和脱敏证据。实例身份、真实 IP、账单、租期、安全组和备份位置保留在 Git 外；密码、私钥、token、真实代理端口和未脱敏遥测永不提交。
3. **M2-min 声明边界**：M2 最小版只证明消费者幂等与重放；transactional outbox 完成前，不宣称已经解决数据库事务与消息发布的原子性。
4. **Compose/k3s 控制权与数据隔离**：两种部署模式互斥，使用隔离的端口、卷和 namespace，并提供独立的迁移与清理路径；通过备份恢复 runbook 交接唯一控制源。

## 后果

- 每份性能、故障和容量报告必须说明拓扑、资源竞争、数据边界和未证明事项。
- 公开作品可复现，但不会泄漏私人运维信息。
- M2 的项目叙事受证据约束，不把局部幂等扩大成端到端原子性。
- 引入 k3s 时必须先设计与 Compose 的状态交接，不能让两套控制面同时操作同一数据。

## 备选方案

- 到对应阶段再临时决定：拒绝。这四项会跨越多个阶段，晚决定容易造成公开信息泄漏、实验口径漂移或状态破坏。
- 为个人项目提前建立完整多环境平台：拒绝。成本与复杂度不符合当前阶段，明确护栏和可验证交接已经足够。
